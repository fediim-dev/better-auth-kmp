# Skill: Contract-First Coding

Instructions for any coding agent **writing new code** in a project that follows the AI-First Documentation standard (`spec/ai-first-documentation-spec.md`). Companion to `inline-ai-doc-encoder/SKILL.md` (how to write the docs themselves) and `manifest-navigation/SKILL.md` (how to read existing code). Self-contained.

## Why this order

Code and its documentation are born together or the documentation is born wrong. Writing the contract before the implementation gives you a mini-spec to implement against, and forces API decisions (units, errors, threading) to be made deliberately instead of falling out of whatever the first implementation happened to do.

## Procedure for any new public symbol

### 1. Discover before you create

Before writing a new class, function, or helper, check whether it already exists:

- Search the project's `ai-context.md` L1 symbol index (or the module-scoped manifest) for symbols with overlapping purpose.
- If a near-match exists, **extend or reuse it** — or, if it is genuinely unsuitable, say why in your change description. Duplicating an existing helper is a defect even if your copy works.
- Check L3 guardrails of the module you are adding to: your new code must not be an instance of a documented `[Anti-Pattern]`.
- Check the design-token matrix before hardcoding any color, dimension, or constant that a token already defines.

### 2. Write the contract first

Before the body, write the signature and the full docstring per `inline-ai-doc-encoder/SKILL.md`:

- one-sentence summary (what + when to use),
- non-obvious contracts: units, ranges, threading, lifecycle, side effects, error behavior,
- `[Invariant]` / `[Anti-Pattern]` where you already know them.

This docstring is now the spec for step 3. If you cannot write the summary in one sentence, the symbol is doing too much — split it before implementing.

### 3. Implement to the contract

Write the body until every statement in the docstring is true. If the implementation forces a contract change (different error behavior, new side effect), **update the docstring in the same edit and treat it as an API decision** — mention it in your summary to the user, don't let it drift silently.

### 4. Recipe and registration

- New **component** (a symbol others will compose): add one minimal `[Recipe]` that compiles against the final API.
- New **module/package**: add the module-level docstring (purpose, 2–3 entry points, forbidden dependencies) and register the module in the project's docs config (`ai-docs.config.json` or equivalent) so it enters the manifest.

### 5. Finish protocol

Before ending the change:

- [ ] Discovery was done — no duplicate of an existing symbol was created.
- [ ] Every new public symbol's docstring passed the `inline-ai-doc-encoder` checklist.
- [ ] Recipes compile against the code as committed.
- [ ] Manifests recompiled (`ai-docs compile` or project equivalent) so `ai-context.md` includes the new symbols.
- [ ] Docs lint (`ai-docs lint`) passes; no new undocumented public symbols.

## Scope notes

- **Private/internal symbols**: steps 1 and 3 apply (don't duplicate, keep names honest); docstrings optional — prefer better naming.
- **Prototypes/spikes**: mark the module as excluded from the manifest rather than shipping half-true contracts. A wrong contract is worse than no contract.
- **Refactors that move public symbols**: the manifest's `sourceLocation` entries are regenerated by compile — just run the finish protocol; never hand-edit manifests.
