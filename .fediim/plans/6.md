## Alternatives considered
A1 Passkeys reimplements HTTP using only core's public API — duplicates Bearer/X-API-Key/epoch-fenced capture and still needs public `config`/`tokenStorage` getters: a wider, riskier surface than the opt-in I2/I3.
A2 Passkey endpoints in core (`client.passkeys`), passkeys module holds only bridges — contradicts spec Task 2 and C7's "passkeys stay out of core".
A3 Ktor `HttpCookies` with a filtered `CookiesStorage` — a general cookie jar on the shared client (session cookies could travel next to Bearer), custom storage code to scope it, no effect in browsers (operator chose option A, L1).
A4 Full software WebAuthn ceremony in jvmTest (ES256 + CBOR/COSE "none") — ~150 lines of test crypto mostly verifying itself; the SDK side is pass-through (T8/T9) plus challenge replay, proven by T14's paired codes.
A5 One shared `webMain` glue for js and wasmJs — js gets DOM types and `dynamic` from its stdlib while wasm has neither and needs `JsAny`-typed `js()` externals, so shared glue would be written in the wasm interop style and lose js's typed DOM; `kotlinx-browser` is not approved.
